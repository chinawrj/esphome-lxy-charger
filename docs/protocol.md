# BLE 充电器协议参考

以下内容来自受控 GATT 通信观察和配置读回验证。实现仅覆盖已确认的配置查询、状态查询和电压/电流设定；不包含设备身份信息或原始抓包。

## GATT 通道

| 用途 | UUID | 操作 |
|---|---|---|
| 主服务 | `FFF0` | 按 UUID 发现 |
| 设备回复 | `FFF1` | Notify，先订阅 CCCD `2902` |
| 客户端命令 | `FFF2` | Write Without Response / ATT Write Command |

连接后发现句柄，不硬编码 ATT handle。等待通知订阅确认后再查询或设置。

## 帧格式

```text
5E 5E | L | CMD | DATA... | CHECKSUM
```

- `L`：单字节，等于总帧长减 3，也等于 `DATA` 长度加 2。
- `CHECKSUM`：从 `L` 开始到 `DATA` 最后一字节逐字节 XOR。
- 有效帧从 `L` 到 `CHECKSUM` 全部 XOR 的结果为 `00`。
- 通知边界不作为帧边界：实现需要支持分包、合包、校验及重新同步。

## 已确认命令

| CMD | DATA | 用途 / 回复 |
|---|---|---|
| `02` | `01` | 查询配置；回复 `82` |
| `03` | `01 VH VL IH IL` | 设置电压和电流；回复 `83` 回显 |
| `04` | 无 | 查询状态；回复 `84`，目前保留原始内容 |

配置中的两个数值都是 **无符号 16 位大端整数，单位为 0.1 V / 0.1 A**：

```text
voltage = ((VH << 8) | VL) / 10
current = ((IH << 8) | IL) / 10
```

`82` 和 `83` 的已确认数据结构也为 `01 VH VL IH IL`。

查询示例：

```text
读取配置 TX: 5E 5E 03 02 01 00
配置回复 RX: 5E 5E 07 82 01 02 48 00 33 FD
             → 58.4 V / 5.1 A

读取状态 TX: 5E 5E 02 04 06
```

设置与回显示例：

| 设置目标 | CMD 03 发送帧 | CMD 83 回显帧 |
|---|---|---|
| 58.4 V / 5.0 A | `5E5E070301024800327D` | `5E5E07830102480032FD` |
| 58.4 V / 5.1 A | `5E5E070301024800337C` | `5E5E07830102480033FC` |
| 58.3 V / 5.1 A | `5E5E0703010247003373` | `5E5E07830102470033F3` |

## 确认设置的流程

1. 发送一次 `03`。
2. 等待电压、电流均匹配的 `83` 回显。
3. 再发送独立的 `02 / 01` 查询。
4. 将 `82` 返回值与本次目标比较。

ATT 无响应写入提交成功以及 Web 请求返回 HTTP 200，都不代表充电器确认成功。`83` 是数据回显；独立 `82` 读回才用于确认当前配置。

已确认的帧没有事务序号。实现一次只保留一个查询/设置事务；超时、错误回显或断连后的结果应标为失败或未知，并重建连接，避免把迟到回复分配给下一次操作。设置命令不自动重发。模块间事件的 `request_id` 仅用于本机内部关联，不属于 BLE 线协议。

后台状态查询也需要串行：观察到的手机通信全部按请求、回复、下一请求交替进行。实机定向测试中，`04` 尚未收到 `84` 就插入 `02`，两次均没有收到对应 `82`；先收到 `84` 再发 `02` 则成功。因此固件在 `84` 返回前保留新请求，不将其与状态轮询同时发送。该观察没有确立固定的最小毫秒间隔。

## 范围与未确认内容

当前程序限制为 **58.2–58.4 V、4.9–5.1 A，步长 0.1**。这是已观察的测试范围，不是充电器完整规格，也不是任何电池的安全范围。

尚未充分确认的内容包括：`84` 中的实际输出电压、电流、温度、故障位和输出开关字段，以及输出开启/关闭命令、断电保存行为、更宽设置范围和其他设备版本的兼容性。配置读回成功不等于实际电气输出达标或断电后仍保留配置。

### `84` 实时字段的证据边界

复查最初的 408 笔状态回复，均为 20 字节且 XOR 正确，只有 4 种载荷。以 CMD 后第一个字节为 DATA[0]：DATA[4] 只出现 0/1；DATA[10] 从 28 变化到 30；DATA[11] 恒为 28；其余均为 0。操作者当时观察到实际电压约 0–0.1 V、电流 0 A。这些样本无法区分电压的字节宽度/字节序，也无法定位电流字段；温度归属同样未确立。

因此不能把零值候选当作已验证的实时电流。新增实时事件和 LCD/Web 显示接口，与 `84` 字段解码的验证是独立事项。后续可通过与本机帧格式匹配的厂家协议、原控制程序的解析实现，或充分的同步读数与原始帧对照来确认偏移、字节宽度、字节序、倍率和无效值语义。当前空载的零值样本不足以单独确立这些字段。

如果采用实测反推，需要能区分候选布局的多个实际 V/A 变化点；非零电流是其中一种有用证据，但不是继续查协议的唯一途径。不能把配置值当作实际读数，也不要求操作者仅为协议分析接入电池或负载。


### 重启抓包后的电压解析（v2.1）

在操作者重启空载充电器后，保持设定值 58.4 V / 5.1 A 不变，Web 原始状态观察出现了新的完整 `84` 帧。该记录是带时间戳的轮询观察，不把重复读到同一帧计为独立 BLE 通知。新样本 XOR 均正确；DATA[3:5] 出现 `024B`、`024C`、`024D`、`024E`，随后还观察到 `0103`、`0000`。

当前实现采用 **`((DATA[3] << 8) | DATA[4]) / 10.0` V**，对应 58.7、58.8、58.9、59.0、25.9、0.0 V。完整应用帧偏移为 7、8；例如：

```text
5E5E1184000000024C00000000002022010000D8
              ^^^^ DATA[3:5] = 024C -> 58.8 V（推定映射）
```

这是一项**依据字节变化、重启过程和既有电压量级的推定**，不是厂家定义，也未与原小程序或万用表同步核验。操作者选择不再使用小程序，并明确要求先实现当前可推定的解析。因此 LCD 明示“电压待核”，Web 状态标注 `inferred mapping`。配置中的 58.4 V 始终独立，不参与生成输出数值；本次观察不能证明绝对电气准确性。

解析器要求完整 20 字节、`5E5E/11/84` 格式与有效 XOR；针对本次 58.4 V 设备，使用 0–100 V 合理性门槛，越界即无效，不截断成上限。这是解析防护，并非设备额定范围或已确认的故障值协议。数据无效、达到 6 秒未更新或断连时隐藏旧读数。

**实时电流按操作者要求暂缓，等待以后有电池时再继续验证。** 即使载荷中的候选电流字节为零，也不发布 0 A；温度、输出开关和其他状态位仍未解析。
